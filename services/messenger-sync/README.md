# messenger-sync

## Design notes

- `messenger-mcp` has no Traefik route. The server has no authentication of its own, so network isolation inside homelab-network is the whole of its access control. MCPHub reaches it at `http://messenger-mcp:8000/mcp`.
- Both services drop all capabilities and set `no-new-privileges`. Nothing needs a capability, and the harvester runs Chromium with `--no-sandbox`, so the container is the boundary.
- `messenger-mcp` has no `env_file` and, deliberately, no profile volume. It has no way to reach Messenger even if the code were wrong: no browser profile is mounted into it.
- `MESSENGER_MCP_ALLOWED_HOSTS` is rmcp's DNS-rebinding guard: the `Host` headers `/mcp` answers. MCPHub addresses the server by container name. Unset means loopback only, which returns 403 for every call while `/healthz` stays green: a container that looks healthy and answers nothing.
- `messenger-harvest` is the only container with a browser profile, and the only one with DDL rights: it applies the migrations at boot. It exposes no port, because nothing calls it.
- `messenger-harvest` has no healthcheck. It sleeps about 15 minutes between passes by design, which no probe can tell apart from wedged. Use the MCP status tool instead.
- The profile lives under `quick/apps`, where every other stack keeps its data. The previous path named a dataset that does not exist. Docker answers a missing bind source by creating it, so the deploy would have succeeded and quietly kept the credential on the boot pool.
- The profile directory is the Messenger credential: cookies, the Signal identity key and the device registration. Meta rotates the session cookie while the browser runs, so it must persist across passes. A fresh profile every time would mean a fresh device registration every time, which is the loudest possible signal.
- Memory limit is 3 GiB. An ordinary pass measured a 718 MiB peak, settling to about 450 MiB, so 1 GiB was that peak plus headroom, and for an ordinary pass it still is. A backwards walk through a conversation is different: Messenger adds DOM for every screen scrolled back and never releases it, so the walk is a memory ramp. At 1 GiB the renderer died after 30 to 72 screens, collecting 274 and 330 rows against threads holding 22,433. The walk could not even climb back to the line the previous pass stopped at, so the backfill plateaued at about 2%. The host has 62 GiB with about 7 GiB spare. It is still a cap and not a reservation: the memory is held only while a pass is running, and only a backwards walk reaches for it. It raises the ceiling and does not remove it, because one browser can only hold so much of a 22,433-message conversation, whatever the number here.
- `shm_size` is raised because Chromium needs more than the default 64 MB of shared memory. Without it Chromium crashes rendering tabs, which surfaces as an unexplained page-load timeout.
- `init: true` runs tini as PID 1 purely to reap children. Chromium reparents its exited helpers to PID 1, which here is the Python entrypoint, and Python never calls `wait()` on children it did not start, so every pass left zombies behind. 48 were measured in three hours (32 `chrome`, 16 `chrome_crashpad`). Closing the browser between passes does not help, because the leak is in who reaps them rather than when they exit. It is harmless for a container that restarts often and not for one on `unless-stopped`.
